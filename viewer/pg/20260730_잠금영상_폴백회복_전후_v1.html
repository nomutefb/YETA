잠금 히어로 영상 — 폴백·회복 전/후 v1

운영자 260730 제보 「이 화면에 영상 안움직이는 버그있음」. 재현 결과 앱 재생 로직은 정상이었고, 실제 결함은 #ymVideo가 mp4 단벌 소스 + 실패 시 폴백·재시도·신호가 0이라는 쪽이었다 — 소스를 한 번 못 물면 포스터가 영구 고정되고 새로고침 말고는 복구 경로가 없었다. 아래 왼쪽이 그 상태(정지), 오른쪽이 고친 뒤(재생). 실제 잠금 영상 파일을 그대로 띄운 라이브 비교다.

① 움직임 — 실물 비교 (왼쪽은 실제로 멈춰 있다)

전 — 포스터 고정 정지

소스를 못 문 <video>가 남기는 그림 = poster 한 장. 운영자 스크린샷과 같은 프레임이고, 로고 YETA의 E·T·A가 밝은 피부톤 위 반투명 흰색이라 Y만 보이던 것도 여기서 나온 파생 증상이다.

후 — 폴백으로 재생 재생

소스 2벌(mp4 → webm). H.264 되는 브라우저는 mp4, 못 쓰는 브라우저는 VP9로 착지한다. 이 칸이 움직이면 그 브라우저에서는 고쳐진 것.

③ 무엇을 바꿨나

  • 소스 2벌 — #ymVideo에 lock-hero.webm(VP9 2.57MB) 추가. 바로 아래 언락 배경 #ybgvidEl이 원래 쓰던 이중 소스 관용을 그대로 계승했다. 순서가 mp4 → webm인 건 의도 — 브라우저는 첫 지원 소스만 받고, 두 벌 용량이 사실상 같은데(2.58 / 2.57MB) H.264 쪽이 하드웨어 디코딩이 훨씬 넓어 60fps 클립에서 배터리·발열이 유리하다.
  • 재생 판정 단일 관문 yVidPlay — 잠금 히어로에서 HTML autoplay 속성을 뺐다. 속성이 붙어 있으면 브라우저가 판정을 앞질러 재생해버려서 코드 주석이 선언한 「reduce = 포스터 정지」 계약이 잠금 화면에서만 새고 있었다. 이제 설정 적용·탭 복귀·첫 조작 세 경로가 전부 이 함수를 지난다.
  • 회복 훅 — 캡처 단계 위임 1핸들러. 실측 함정 하나를 여기서 잡았다: <source> 자식을 쓰면 전부 실패해도 <video>에는 error가 안 온다(스펙 — error는 각 <source>에만 오고 v.error는 null로 남는다). 그래서 소스 쪽 이벤트를 부모로 접어 받되, 첫 소스 실패는 정상 폴백에서도 뜨므로 1.5초 뒤 실제 상태(networkState 3 = 소스 전멸)로만 재시도한다. 리스너보다 먼저 죽는 경우(즉시 실패)는 load 시점 상태 점검이 한 겹 더 받는다.
  • 탭 숨김 정지 — visibilitychange 정지 대상이 언락 배경뿐이라 잠금 히어로만 빠져 있던 짝을 맞췄다.

새 :root 토큰·색·간격·모션 = 0. 추가분은 영상 파일 1개와 스크립트 로직뿐이고, 이 시안의 표면 CSS도 20260730_최산_배경이관_전후_v1.html을 그대로 계승했다.

④ 검증

  • 재현 — H.264 미탑재 헤드리스 chromium 1194에서 운영자 스크린샷과 동일 프레임의 포스터 고정 재현. 같은 브라우저에 재생 가능한 소스만 물리면 정상 재생 = 앱 로직 무결 확인.
  • 파일·서버 무결 — lock-hero.mp4 = h264 High, 640×1138, 60fps, 9.97s, moov 선두. 라이브 yeta.soong.kr도 200 · video/mp4 · Range 206 정상. 즉 결함은 서버·파일이 아니라 클라이언트에서 실패했을 때의 처리였다.
  • 후 검증 — 위 ② 표 7행을 헤드리스로 전수 실측, 기대치 전부 일치. check_refs rc=0.
  • 미검증(명시) — 운영자 브라우저에서 mp4가 실패한 정확한 이유(코덱 미탑재 / 자동재생 차단 / 확장·실드 차단)는 원격에서 특정할 수 없었다. 이번 수정은 세 원인 모두를 같은 착지점(재생)으로 보내는 처방이라 원인 특정 없이도 해소되지만, 그래도 안 움직이면 그 화면에서 document.getElementById('ymVideo').networkState 값을 알려주면 바로 좁혀진다.
